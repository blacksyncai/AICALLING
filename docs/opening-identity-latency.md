# Opening identity turn latency fix

A retained production trace from deployment `c05e4bd8-8c79-42de-ad12-45a625969f7e` shows a complete pipeline waiting on turn commitment: LLM requested at process offset 9549 ms, first model chunk 9749 ms, generated audio 9885 ms, but turn committed only at 11790 ms and worker speaking at 11908 ms. SDK metrics report LLM TTFT .208 s, TTS first frame .130 s, end-of-turn delay **2.501 s**, worker e2e **2.619 s**. The latest Matt deployment had startup logs but no connected call traces when inspected; this evidence establishes a real recent bottleneck, not proof that every reported pause or the latest test used this exact call/provider.

In the installed LiveKit 1.6.4 `AudioRecognition._run_eou_detection`, a semantic probability below `unlikely_threshold` selects the configured `max_delay` (2.5 s). Text/audio speculation already works; it cannot play until turn commitment. Increasing model speed or prompting “answer faster” would not remove this gate.

`OpeningTurnDetector` wraps the existing installed `_TurnDetector` protocol. On only an early identity question ending in a known contact's first/full name, a closed complete answer returns completion probability 1.0. All other cases delegate unchanged to the multilingual model. Names come from existing per-call variables; the agent's own name is not substituted for the caller's name. No name, placeholders, later questions, dictated numbers/addresses, “yes but,” ellipses, or questioning answers use the fast path. “Yes,” “no,” “this is [name],” “it's [name],” and “speaking” are eligible only in that opening context.

This is one turn controller. It does not call commit_user_turn/generate_reply separately, modify chat context, replace the customer's script, change voices/models, lower VAD silence, zero timers, change interruption thresholds, or issue external actions. VAD resumption and transcript changes remain owned by the SDK, as do preemptive generation and cancellation. The existing configured minimum delay still applies; only the unnecessary semantic maximum wait is avoided for this narrow case. Already-overlapping one-word answers may still encounter the existing two-word interruption minimum; that distinct behavior is not claimed fixed here.

The `identity_turn_complete` content-free trace event confirms an actual fast-path hit. `call_config.fast_identity_turns` reports whether it is enabled. `VOICE_FAST_IDENTITY_TURNS` defaults true for this authorized fix; set false and restart workers normally to roll back without changing agent data or other latency work.

Validation includes exact positive/negative opening cases and an integration test running the **actual installed SDK end-of-turn task**, using a stub semantic probability .1 against threshold .7 to reproduce the observed max-delay branch. It measures the old branch, adapted complete answer, and adapted unfinished answer separately. The artificial setup starts .55 s after the speech-end anchor to model an already-detected VAD stop; it is not a microphone, STT, LLM, TTS or SIP benchmark. Expected measured outcome: complete answer commits around .55 s from the anchor instead of 2.5 s, while “yes but” still waits 2.5 s. Caller-audible improvement after deployment still requires a new test call.

Artifacts: `/workspace/blacksync-opening-latency/` contains content-free baseline JSONL, parsed metrics, expandable same-clock timelines, SDK timing test properties and regression results. The six ordinary baseline SDK worker e2e samples have p50 1.776 s / p95 2.614 s; this small sample is not a caller-audibility distribution or a measured post-fix result.
