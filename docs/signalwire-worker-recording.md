# SignalWire worker recording

Confirmed production failure: recent answered SignalWire calls logged LiveKit egress `resource_exhausted`, `egress minutes exceeded`, HTTP 429. Storage credentials were configured. The carrier connected calls, but the separate egress recorder did not start.

SignalWire calls now use the existing worker RecorderIO capture path (also used for opted-in browser calls), rather than LiveKit egress. Server-side dispatch checks recording storage readiness and the agent's recording preference, stores the recording key, and adds worker recording metadata. Both configurable and legacy workers attach the recorder after session audio initialization and before the opening. Caller input and agent output are encoded on a background thread to stereo OGG and uploaded to the existing private bucket at call end. Existing playback/download and account checks are unchanged. This records the agent session, not an entire downstream transferred call or independent background room tracks.

The per-boot authenticated internal recording-state endpoint checks the call's room and worker-specific state. It accepts no client-provided object key or URL. Terminal states are idempotent and cannot be regressed by late events. Failed starts/uploads clear the key so playback does not remain perpetually processing. Unanswered/failed dials clear pending worker recordings. Call outcomes are persisted before upload, and recording failure does not drop the call. Status reporting during recording startup runs in the background so it adds no API wait to the greeting. Recorder close and upload each have a 30-second bound, with the worker shutdown allowance increased to 90 seconds. Interrupted/failed uploads have no automatic replay/spool and may lose the recording; this is not presented as durable storage before upload succeeds.

No SignalWire recording charge or LiveKit egress quota change is made by this implementation. The app still uses its existing storage; normal storage/compute costs apply. Twilio and Bandwidth recording paths are unchanged. Historical audio never captured cannot be reconstructed from these changes.

Validation: 28 backend checks passed, including actual SDK/PyAV two-channel encoding and decoding of distinct simulated audio tones, single upload, upload failure cleanup, missing audio cleanup, SignalWire recording metadata without egress, internal endpoint authentication/room matching, late-status protection, unanswered-call cleanup and existing phone/Twilio regressions. No live call was placed as part of testing; production call capture and playback still require a new call after deployment. No frontend changed.
